# Architectural Decisions Log (DECISIONS.md)

This document serves as the master engineering log for the Streaming Lakehouse CDC project. It details the core technologies chosen, the rationale behind those choices, and the technical bottlenecks encountered and overcome during development.

---

## 1. Storage Format: Apache Iceberg
**Decision:** We selected Apache Iceberg as the open table format over Delta Lake and Apache Hudi.
**Rationale:** 
- **Catalog Integration:** Iceberg strictly separates the data layer from the metadata layer and integrates flawlessly with the Hive Metastore. This allowed us to track schema evolution and partition changes seamlessly.
- **Hidden Partitioning:** Iceberg's hidden partitioning prevented the need to add partition columns to our raw CDC events.
- **Time Travel:** Iceberg natively supported snapshot-level time travel and rollback capabilities out-of-the-box, which was critical for Phase 2.

## 2. Streaming Compute: PySpark Structured Streaming
**Decision:** We utilized PySpark for the ingestion pipeline instead of Apache Flink.
**Rationale:**
- **MERGE INTO Support:** Spark SQL's `MERGE INTO` syntax provided an incredibly expressive and powerful way to handle CDC `op` logic (upserts and deletes) within `foreachBatch` micro-batches.
- **Unified Batch/Stream:** Using Spark allowed us to write the ingestion script as a stream, while using the exact same Spark SQL engine to write our batch benchmark scripts (E1 & E2) and maintenance jobs.

## 3. Message Broker: Kafka (KRaft Mode)
**Decision:** We deployed Apache Kafka in KRaft mode (without ZooKeeper).
**Rationale:**
- **Resource Constraints:** Running on a local macOS environment with 16GB of RAM meant every container counted. Dropping ZooKeeper reduced the memory footprint.
- **Simplicity:** KRaft acts as both the controller and broker in a single container, vastly simplifying our `scripts/start_kafka_docker.sh` setup.

## 4. Analytical Engine: ClickHouse
**Decision:** We used ClickHouse for Phase 5 to prove the Decoupled Compute paradigm.
**Rationale:**
- **Native Integration:** ClickHouse possesses a native `file()` and `hdfs()` table function that perfectly parses raw Parquet files generated by other engines.
- **No Data Movement:** We successfully executed aggregations on the Lakehouse data without a dedicated ETL process into ClickHouse.

## 5. Technical Challenges & Trade-Offs

### A. The Embedded Hive Metastore (Derby) Lock-ups
**Challenge:** We used an embedded Derby database for the Hive Metastore to keep the project lightweight. However, Derby only supports a single concurrent connection. If our PySpark ingestion job crashed mid-transaction, Derby would freeze, causing subsequent `DROP TABLE` or `CREATE TABLE` commands to hang indefinitely.
**Resolution:** We built defensive scripting habits. Instead of dropping tables, our benchmark scripts incremented table names (e.g., `orders_mor2`). When Derby locked entirely, we used a hard `kill -9` on the Thrift server inside the Hadoop container and restarted it.

### B. The "Small File Problem" (E1 Benchmark)
**Challenge:** Streaming CDC naturally produces thousands of tiny files over time.
**Resolution:** Our Experiment 1 (E1) benchmark explicitly tracked query planning time as file counts increased from 10 to 5,000. We mathematically proved that planning time degrades non-linearly. By running Iceberg's `rewrite_data_files` (Compaction), we demonstrated planning time dropping from ~30ms down to ~9ms.

### C. Exactly-Once Resilience (E3 Chaos Testing)
**Challenge:** Proving that the system doesn't lose or duplicate data when crashing.
**Resolution:** We built an automated chaos harness that rapidly executed `kill -9` on the PySpark driver. Because Iceberg snapshot commits are atomic, and Spark Structured Streaming perfectly synchronizes its checkpoint offsets with the commit, our `verify.py` script proved 0 duplicates and 0 missing rows across 20 destructive trials.
